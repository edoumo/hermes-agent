## Goals

H2.1 exposes the smallest authenticated control plane needed by Hermes Harness UI while preserving the H1/H2 safety boundaries.

The UI still never opens SQLite directly. The existing Hermes API listener remains the only HTTP listener. The existing API bearer token, CORS middleware, profile multiplexing and session authority remain the trust boundary.

## Routes

Read routes retained from H2:

* `GET /api/sessions/{session_id}/workers`
* `GET /api/sessions/{session_id}/workers/{worker_id}`
* `GET /api/sessions/{session_id}/workers/{worker_id}/messages`
* `GET /api/sessions/{session_id}/workers/{worker_id}/activations`
* `GET /api/sessions/{session_id}/worker-tasks`

H2.1 control routes:

* `POST /api/sessions/{session_id}/workers`
* `POST /api/sessions/{session_id}/workers/{worker_id}/messages`
* `POST /api/sessions/{session_id}/workers/{worker_id}/run`
* `POST /api/sessions/{session_id}/worker-tasks`
* `POST /api/sessions/{session_id}/worker-tasks/{task_id}/status`
* `POST /api/sessions/{session_id}/worker-tasks/{task_id}/dependencies`

Incremental invalidation stream:

* `GET /api/sessions/{session_id}/worker-events`

H2.1 deliberately adds no Durable Worker `DELETE`, `PUT` or `PATCH` route.

The task status mutation uses POST rather than PATCH so browser clients work with the current Hermes CORS method contract without requiring an unrelated core CORS change.

## Worker creation

`POST .../workers` accepts:

* `label`
* `role` (`leaf` or `orchestrator`)
* optional `model`
* optional `toolsets`

Unknown request fields fail closed.

Toolsets must be known Hermes toolsets and must be a subset of the toolsets currently enabled for the `api_server` platform. An API-created Durable Worker therefore cannot broaden the parent API platform's permissions.

## Inbox and idempotency

`POST .../messages` accepts a message and an optional stable `message_id`.

The H1 durable inbox remains authoritative:

* first use of an id creates the message;
* repeating the same id with identical durable content is idempotent;
* repeating the same id with different content is rejected.

No separate HTTP idempotency database is introduced.

## Activation dispatch

`POST .../run` does not execute a second reservation after returning to the caller.

The handler:

1. checks session authority and runtime lock;
2. checks the bounded H2.1 activation capacity;
3. atomically calls `reserve_next_activation()`;
4. obtains the real durable `activation_id` and message id;
5. starts one background execution task;
6. returns HTTP 202 with the durable activation identity immediately.

The background task executes exactly the reservation already persisted by step 3.

The helper `agent/durable_worker_execution.py` uses Hermes' public `SubagentLifecycleService`. It does not implement another agent loop and does not serialize `AIAgent`.

## Timeout contract

H2.1 never sends `timeout_seconds` in `SubagentLaunchRequest`.

Hermes explicitly rejects per-launch timeout values in the public lifecycle API. Any hard child wall-clock policy must therefore remain an operator-level Hermes delegation policy such as `delegation.child_timeout_seconds`.

The older H1 service signature still accepts an optional wait-timeout for internal compatibility, but the H2.1 HTTP surface does not expose it and the new pre-reserved execution seam does not use it.

## Concurrency

The H1 SQLite reservation remains the per-worker cross-process mutex.

H2.1 adds an adapter-level concurrent activation cap for API-dispatched Durable Worker work. It defaults to 4 and is clamped to the range 1 through 8.

Optional platform extra:

`durable_workers_max_concurrent_activations`

A saturated API dispatcher responds with HTTP 429 and `Retry-After: 1`.

Live H2.1 activation tasks are included in `active_agent_work_count()` so the Gateway drain sees them as real agent work.

## Task DAG writes

H2.1 exposes creation, status transition and dependency creation using the existing H1 store.

Status changes preserve H1 integer revision compare-and-set semantics through `expected_revision`.

Dependency creation preserves H1 cycle detection and parent-session ownership.

The read projection returns both `blocked_by` and derived `ready`, so Hermes Harness UI never needs to reimplement DAG readiness rules.

## SSE invalidation stream

The event stream is intentionally an invalidation feed, not a second durable event database.

It emits:

`event: durable_workers.changed`

with:

* `session_id`
* opaque `change_token`
* event timestamp

The token is a SHA256 of session-scoped aggregate public state. It changes when workers, inbox state, activation state, task state or task dependencies change, including activation binding from `STARTING` to `RUNNING`.

The client then refetches the relevant bounded GET projection.

This keeps SQLite as the durable truth and prevents an in-memory event stream from becoming an alternative state model.

## SSE reconnect

The stream emits the opaque token as the SSE event id.

`Last-Event-ID` accepts only:

* `empty`
* a 64-character lowercase hexadecimal change token

An unchanged token is not emitted again after reconnect.

The server sends comment keepalives approximately every 20 seconds.

The stream is bounded to 16 simultaneous subscribers per adapter instance.

## Browser authentication

The feed uses the same bearer authentication as the rest of Hermes API.

No API token is accepted in query parameters.

A browser implementation that cannot attach an Authorization header through native `EventSource` must use an authenticated `fetch()` streaming client or an equivalent SSE parser. This is intentional: avoiding token-bearing URLs is more important than native EventSource convenience.

## Privacy and authority

All H2 session-isolation rules remain in force.

Cross-session access fails as not found.

Public activation projections continue to omit:

* `owner_pid`
* `owner_started_at`

The SSE token contains no transcript, PID, model output or secret material.

## Deliberately deferred controls

H2.1 does not yet expose:

* worker deletion;
* worker metadata update;
* durable activation steer;
* durable activation cancel;
* direct task deletion;
* a durable fine-grained event ledger;
* canonical migration of `durable-workers.db` into `state.db`.

Those controls should be added only after the current write and event contract passes real Hermes qualification.

* SSE invalidation and `Last-Event-ID` behavior;
