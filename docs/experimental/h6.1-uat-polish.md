## Why H6.1 exists

H6 itself remains technically qualified. H6.1 is a focused product/UX follow-up
created from the first human UAT before any upstream PR. It does not introduce a
new scheduler, storage schema, worker execution model, listener, or task-DAG
semantic.

The UAT showed two missing operator capabilities in the backend contract:

- an existing durable worker had no supported way to change its label/model/toolsets;
- an obsolete durable worker could be created but not safely removed from normal use.

## Worker preferences

`ManagedVersionedDurableWorkerStore` extends the H6 versioned store with a
revision-CAS preference update for:

- label;
- model override (`null` returns to the gateway default);
- toolsets.

A RUNNING worker cannot be edited. Existing validation and api_server toolset
permission narrowing remain authoritative.

## Archive, not hard delete

H6.1 deliberately does **not** add worker deletion.

A durable worker is identity plus durable transcript, activations, tasks and
audit history. Hard deletion would conflict with that contract and could erase
operator evidence. The UI therefore exposes reversible archive/restore:

- `DORMANT -> DISABLED` archives;
- `DISABLED -> DORMANT` restores;
- transcript, activation, task and audit rows remain intact;
- RUNNING workers cannot be archived;
- FAILED workers cannot be archived and restored as a shortcut around the
  qualified retry/recovery path.

The new API controls are POST-only and session-scoped:

- `/api/sessions/{session_id}/workers/{worker_id}/edit`
- `/api/sessions/{session_id}/workers/{worker_id}/archive`
- `/api/sessions/{session_id}/workers/{worker_id}/restore`

H6.1 adds no DELETE route and no storage migration.

## Qualification boundary

H6 PASS evidence remains authoritative for unchanged execution/storage paths.
The targeted H6.1 qualification must prove:

- H1-H6 consolidated backend tests remain green;
- new preference/archive unit and API tests are green;
- model edit changes the model used by a subsequent real activation;
- archive preserves all durable history and blocks dispatch while archived;
- restore returns a worker to normal DORMANT operation;
- FAILED recovery semantics cannot be bypassed by archive/restore;
- session isolation and auth remain fail-closed;
- no principal runtime/configuration is touched.

No PR, merge, main update, or principal runtime mutation is authorized by this
document.
